## 一、从痛点出发：多平台接入的困境

接入飞书机器人的经历，很多开发者都踩过坑：接入文档看三天，SDK 调通又是两天，好不容易跑通了，下次接钉钉又得重来一遍——钉钉的消息格式、回调接口、鉴权方式都和飞书不同，每换一个平台，之前的工作几乎无法复用。

这个架构最初的需求很简单：**能不能写一次 Agent 逻辑，然后随便接哪个 IM 平台都行？**

答案是：能。靠的是消息总线（Message Bus）。

在传统架构里，Channel（渠道）和 Agent 是紧耦合的——飞书消息来了直接调 Agent，Agent 回复再直接塞回飞书。一旦要加一个钉钉，要么改 Agent 代码，要么在 Agent 外面再裹一层转发脚本，越往后越难维护。

消息总线的做法是把 Channel 和 Agent **完全解耦**：Channel 只负责收发消息，收到消息后扔进队列；Agent 从队列里取消息处理，处理完再扔进另一个队列；Channel 从那个队列里取走响应发出。整个过程没有任何 Channel 和 Agent 之间的直接调用。

接入一个新渠道需要做什么？实现三个接口：`start()`、`stop()`、`send()`。Agent 那边的代码，一行不用动。

## 二、核心设计哲学：总线即边界

解耦说起来容易，做起来需要一条清晰的边界来划定职责。这个架构用**消息总线**作为边界。

消息总线本质上是两个异步队列：`InboundQueue` 接收来自各个渠道的消息，`OutboundQueue` 存放 Agent 的响应。Channel 只和 InboundQueue 打交道，Agent 只和 OutboundQueue 打交道，两者互不感知。

![](https://image-static.segmentfault.com/926/559/926559324-6a26d73fdf8a8)

这条边界的价值是**扩展方向的可预测性**：新增一个渠道，Agent 不需要知道。只需写一个 Channel 实现，把消息扔进 InboundQueue，剩下的流程自动流转。换一个 LLM Provider、加一套新的工具集，渠道也完全不受影响。这条线画清楚后，系统的各部分就可以独立迭代，不必担心改一处动全身。

**为什么要自己造轮子？** 可能有人会问：LangChain Agent、Coze、甚至直接用 OpenAI 的 Assistant API，都有工具调用和对话管理能力，为什么要自己实现这一套？

核心原因是**控制粒度**。现有框架大多把 Channel 接入、消息总线、LLM 调用、工具执行包装在一个黑盒里。要在某个环节做定制——改重试策略、加特殊权限校验、接入官方 SDK 不支持的 IM 平台——会发现改动空间非常有限，要么等框架支持，要么 fork 后自己维护。

这个架构把所有边界设计成**显式接口**，没有隐藏的胶水代码。每个组件的职责边界清晰，替换成本低，调试路径短。代价是这个架构不是"五分钟接入"，而是需要理解每个抽象层的设计意图。适合需要深度定制的团队；不需要这么细粒度控制的团队，用 LangChain 也没问题。

## 三、分层架构一览

整体架构分为四层，每一层都有明确的职责边界：

![](https://image-static.segmentfault.com/155/369/1553693416-6a26d7421a162)

|层级|职责|稳定性|
|---|---|---|
|渠道层（Channels）|接入各类 IM 平台，处理协议差异|易变，频繁新增|
|消息总线（Bus）|异步解耦，不关心内容|最稳定，几乎不变|
|核心 Agent 层|上下文构建、工具调度、会话管理|稳定，慢速迭代|
|Provider / 工具层|LLM 调用、工具执行|稳定，但会扩展|

总线层是最稳定的部分。渠道来来去去，Provider 换来换去，只要总线的接口不变，核心 Agent 的代码不需要任何改动。这正是好边界的特征——**让变化的部分独立演化，让不变的部分保持稳定。**

## 四、核心组件解析

### 4.1 渠道层：即插即用的接入设计

**核心问题：如何抹平不同 IM 平台的协议差异？**

方案是 `BaseChannel` 抽象。所有渠道实现都继承它：

![](https://image-static.segmentfault.com/648/932/648932836-6a26d7452f4c9)

继承 `BaseChannel` 的渠道只需实现三个抽象方法：`start()` 建立与 IM 平台的连接并开始监听消息；`stop()` 做清理；`send()` 将 Agent 的响应发回用户。这三个方法之外的一切——消息格式解析、协议适配、事件循环——都由具体渠道自行处理，核心 Agent 无需感知。

**权限控制**是 Channel 层的重要功能。`is_allowed()` 方法支持白名单机制：配置 `allow_from = ["*"]` 允许所有人访问，配置具体 ID 列表则只放行指定用户。空列表默认拒绝所有请求，避免测试环境误开导致安全问题。

`transcribe_audio()` 方法内置语音转写能力。渠道可以调用 Whisper（OpenAI 或 Groq）将语音消息转成文字后再交由 Agent 处理，无需自行实现这一逻辑。

`send_delta()` 是可选的流式接口。当渠道实现这个方法后，Agent 在生成响应的过程中可以逐步推送文本片段，用户看到的是"打字机"效果而不是等几秒才看到完整回复。并非所有渠道都适合流式（比如邮件渠道），所以这是可选项。

---

### 4.2 消息总线：异步队列背后的并发模型

**核心问题：如何保证多渠道并发时不乱了序、不阻塞？**

MessageBus 的实现很轻量：两个 `asyncio.Queue`，四个发布/消费方法。没有复杂的路由逻辑，没有中间件，就是一个纯粹的异步队列对。

![](https://image-static.segmentfault.com/224/756/2247567053-6a26d74790323)

`asyncio.Queue` 本身是协程安全的，多个 Channel 同时 `publish_inbound()` 和 Agent 调用 `consume_inbound()` 不会产生竞争条件，不需要额外的锁保护队列操作。复用已有安全保证，减少潜在 bug。

`inbound_size` 和 `outbound_size` 两个属性用于监控——可实时看到消息积压情况，便于在系统过载时报警或触发流控。

**多渠道并发的调度规则：同 Session 串行，不同 Session 并发。** 如果一个 Session 正在处理消息，新消息会进入该 Session 的 `_pending_queues` 排队等待；如果没有正在处理的 Session，则为这条消息创建一个 `asyncio.Task` 并发执行。飞书和钉钉同时来消息，两者互不阻塞；同一个飞书群的多条连续消息会按顺序处理，不会乱序。

### 4.3 LLM Provider 层：统一接口的背后

**核心问题：不同模型 API 差异巨大，如何抹平差异并提供可靠的重试机制？**

Anthropic 用 `betas thinking`，OpenAI 用 function calling，DeepSeek 返回 `reasoning_content`，各家错误码格式也不同。Provider 层的目标是抹平这些差异，让 Agent 核心只用一套接口。

![](https://image-static.segmentfault.com/281/556/2815565937-6a26d74bc5312)

`LLMResponse` 是所有 Provider 的统一返回格式。`error_should_retry` 字段是关键：它把"这个错误是否应该重试"的判断从调用方下沉到 Provider 内部。Agent 不需要知道什么是 `rate_limit_exceeded`，只需看 `error_should_retry` 是 true 还是 false。

**重试策略采用指数退避：**

- • 标准模式：1s → 2s → 4s，最多 3 次
- • 持久模式：最长 60s 延迟，适合长时间后台任务

还有实用降级处理：当 LLM 返回非瞬时错误（比如因图片内容导致解析失败）时，系统会尝试**去除图片内容后重试**。降级逻辑在 Provider 层实现，调用方无感知。

---

### 4.4 工具系统：动态注册与安全执行

**核心问题：如何让 LLM 安全、可控地调用外部工具？**

工具系统由 `ToolRegistry` 统一管理，支持静态注册（启动时）和动态注册（运行时 MCP 工具）：

![](https://image-static.segmentfault.com/221/478/2214781165-6a26d74e2c255)

每次工具注册/注销，`_cached_definitions` 都会失效并重新缓存，保证传给 LLM 的工具定义列表顺序稳定——这对部分模型的可重复性很重要。

`prepare_call()` 是工具调用的门卫，做三件事：

1. 1. **类型检查**：防止 LLM 传了数组当字典参数
2. 2. **参数校验**：每个 Tool 的 `validate_params()` 实现自己的校验逻辑
3. 3. **错误处理**：校验失败时返回格式化的错误信息，引导 LLM 重试

`execute()` 是实际执行层，所有的 `try/catch` 集中在这里，工具执行失败不会波及 Agent 核心的稳定性。

工具调用由 AgentLoop 统一调度，内部维护一个迭代计数器，每次工具执行后递增。当计数超过配置上限（默认 200 次），AgentLoop 会停止执行并向用户返回超时提示，防止 LLM 进入工具调用的无限循环。这个上限值可通过配置调整，适合对简单任务设置更严格限制。

### 4.5 记忆与会话管理

**核心问题：对话历史越来越长，LLM 的上下文窗口有限，如何在两者之间找平衡？**

![](https://image-static.segmentfault.com/249/140/2491407022-6a26d7505161a)

**Session** 是会话的基本单元。Session key 默认格式为 `channel:chat_id`。当消息携带的 key 在 SessionManager 中不存在时，`get_or_create()` 会自动创建新 Session——Session 创建没有显式接口，本质上是消息驱动的隐式行为。

消息在写入队列的同时会持久化到 JSONL 文件。顺序是：先落盘，再入队列。即使 Agent 进程在处理过程中崩溃，重启后可以读取 Session 的已有消息重建上下文，用户不会丢失正在进行中的对话。

**Consolidator**（会话压缩）负责控制历史长度。当消息数超过阈值（默认 120 条），Consolidator 会将早期消息合并为一条摘要，保留约 50% 的 token 预算。合并后的消息在历史中标记 `last_consolidated`，下次压缩时跳过已处理部分，避免重复压缩导致信息损耗。

**MemoryStore** 负责长期记忆的读写，文件包括 `MEMORY.md`（重要事实和结论）、`SOUL.md`（Agent 人格）、`USER.md`（用户偏好）。这些文件在每次构建上下文时都会被读取并注入 prompt。

**Dream** 是定时执行的记忆整合器，每隔两小时运行一次，分析最近的对话历史，提炼出值得写入长期记忆的洞察并更新 MEMORY.md。这是系统"学习"的机制——每次 Dream 运行完，系统对用户的理解都会多一点。

## 五、消息在系统中的完整旅程

用一张时序图总结一条消息从进入系统到收到响应的完整路径：

![](https://image-static.segmentfault.com/370/895/3708955365-6a26d753013ee)

**响应分发机制：** AgentLoop 调用 `publish_outbound()` 时，消息里带着目标 channel 字段。所有 Channel 都在并发监听同一个 outbound 队列，各自判断"这条消息是不是发给我的"——是的就发送，不是就跳过。Agent 不需要知道当前接入了几个 Channel，不需要维护路由表。这种"各取所需"的设计让 Channel 接入/移除对 Agent 完全透明。

整个链路没有回头路——消息从 User 进，从 User 出，中间经过的每一个组件各司其职，顺序推进。这就是消息总线作为架构边界带来的最大收益：**整个系统的行为是高度可预测的。**

## 六、什么场景适合这个架构？

这套架构不是银弹。适合以下场景：

- • 需要接入多个 IM 平台，且平台间协议差异大
- • 需要深度定制某个环节（重试策略、工具执行沙箱、权限控制等）
- • 团队有足够工程能力维护自建系统
- • 对系统行为有高度可预测性要求

不适合以下场景：

- • 只需接入一个平台，且官方 SDK 够用
- • 快速验证概念，不需要长期维护
- • 团队资源有限，无法承担自建系统的维护成本

如果不确定是否需要这套架构，建议先用 LangChain 等框架快速验证，到确实需要更细粒度控制时再考虑自建。架构复杂度是为了解决问题服务的，不是目的本身。
