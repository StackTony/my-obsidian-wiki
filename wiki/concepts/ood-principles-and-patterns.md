# 面向对象设计原则与模式

软件设计的艺术，是对"变化"的辩证处理：发现变化，隔离变化，以不变应万万变。六大设计原则提供抽象方向，23种GoF设计模式提供具体解法，架构模式定义系统级组织方案。

## 六大设计原则

| 原则 | 英文名称 | 核心思想 | 解决的"变化" |
|------|----------|----------|-------------|
| 面向接口编程 | Program To An Interface | 使用接口继承而非实现继承 | 实现细节变化 |
| 依赖倒置 | Dependency Inversion | 高层和低层都依赖于抽象 | 低层模块变化 |
| 组合优于继承 | Favor Composition | 优先使用组合获得更好设计 | 子类组合爆炸 |
| 单一职责 | Single Responsibility | 一个类只负责一个功能 | 多方向变化 |
| 开放-封闭 | Open-Closed | 对扩展开放，对修改封闭 | 功能需求扩展 |
| Liskov替换 | Liskov Substitution | 子类必须能替换父类 | 子类行为不一致 |

### 面向接口编程（Program To An Interface）

使用"接口继承"而非"实现继承"。接口关注对象概貌，将"不变"的信息抽象出来，不涉及细节，因此是"稳定"的。

好处：Client只关注业务活动（如驾驶），不必关心具体实现；对象可被实现相同接口的另一个对象替换；松散耦合，增加重用可能性。

### 依赖倒置原则（DIP）

高层模块不应依赖低层模块，二者都应依赖抽象。抽象的稳定性决定系统的稳定性。

### 组合优于继承

继承被过度使用的两个问题：子类组合数目几何级增长、子类类型编译时确定不能运行时动态改变。

组合的正确使用场景：优先组合获得重用性与简单性更佳的设计，配合使用继承扩充可用的组合类集。

继承仅当：子类表达"是一个父类的特殊类型"而非"是一个由父类所扮演的角色"；子类实例永远不需转化为其他类对象；子类扩展父类职责而非重写或废除。

### 单一职责（SRP）

职责=功能=引起变化的原因。当一个类有两个以上变化方向，会产生过多变化点。解决方案：拆分变化。

### 开放-封闭法则（OCP）

OCP是OO设计的真正核心：可以添加新代码扩展系统行为，但不能修改已有代码。一个系统不可能所有模块都满足OCP，但应努力最小化不满足OCP的模块数量。

### Liskov替换（LSP）

使用指向基类的引用的函数，必须能在不知道具体派生类对象类型的情况下使用它们。子类型不得具有比基类更多的限制。

## 架构模式 vs 设计模式

| 特性 | 设计模式 | 架构模式 |
|------|----------|----------|
| 规模 | 较小 | 较大 |
| 影响范围 | 单一子系统 | 整个系统基本结构 |
| 作用 | 细化子系统或组件 | 定义整体结构组织 |

### 核心架构模式

| 模式 | 核心思想 | 应用示例 |
|------|----------|----------|
| **Layers** | 每层向上一层提供服务，通过同步过程调用 | ISO OSI七层/TCP/IP/三层企业架构 |
| **MVC** | Model(数据)+View(展示)+Controller(输入)分离 | Smalltalk/Web应用 |
| **Client-Server** | 服务器为多客户提供服务，请求跨机器边界 | Web应用/远程数据库 |
| **Master-Slave** | 主分配工作到从，从并行执行后主汇总 | 容错/并行计算/嵌入式 |
| **Pipe-Filter** | 数据流经管道到过滤器，每步封装为组件 | 编译器/UNIX shell |
| **Broker** | 中介协调通信、转发请求 | CORBA/Web Services |
| **P2P** | 对等模型，每端既客户端又服务器 | 文件共享/多用户协作 |
| **Event-Bus** | 发布者/订阅者异步消息通知 | 过程监控/交易系统 |
| **Blackboard** | 多专家子系统共享黑板数据存储，协作求解 | 无确定性解的复杂问题 ^[inferred] |

## 23种GoF设计模式

### 创建型（5种）— 处理对象创建过程

| 模式 | 定义 | 关键特点 |
|------|------|----------|
| **Factory Method** | 定义创建对象的接口，让子类决定实例化哪个类 | 客户类和工厂类分开；接纳新产品不需修改客户类 |
| **Abstract Factory** | 创建一系列相关或相互依赖对象的接口 | 产品族创建；切换产品族只需切换工厂 |
| **Builder** | 将复杂对象构建与表示分离 | 分步骤建造；强制分步骤过程 |
| **Prototype** | 用原型实例指定创建种类，通过拷贝创建新对象 | 每类须配备克隆方法；product和factory功能合二为一 |
| **Singleton** | 保证类仅有一个实例，提供全局访问点 | 解决性能问题而非耦合问题 |

### 结构型（7种）— 处理类或对象的组合

| 模式 | 定义 | 关键特点 |
|------|------|----------|
| **Adapter** | 把一个类的接口变换成客户端期待的另一种接口 | 使不匹配的类能协同工作 |
| **Bridge** | 将抽象部分与实现部分分离，使它们都可独立变化 | 解决2个方向变化：抽象与行为 |
| **Composite** | 把部分与整体用树结构表示，单对象和组合对象使用一致 | 树形结构的统一处理 |
| **Decorator** | 动态给对象增加功能，可再动态撤销 | 继承的替代方案；Bridge抽象+实现合二为一 |
| **Facade** | 外部与子系统通信通过统一门面对象 | 每子系统一个门面类（单例）；例：JDBC |
| **Flyweight** | 以共享方式高效支持大量细粒度对象 | Hash表共享思想；解决OO性能问题 |
| **Proxy** | 给对象提供代理，由代理控制对源对象的引用 | 代理可扩展被代理者功能（OCP） |

### 行为型（11种）— 处理类或对象的交互和职责分配

| 模式 | 定义 | 关键特点 |
|------|------|----------|
| **Chain of Responsibility** | 请求在链上传递，直到某对象决定处理 | 客户不知链上谁最终处理；请求可不被任何对象接受 |
| **Command** | 把请求/操作封装到对象中 | 解耦调用者与提供者；支持撤销 |
| **Interpreter** | 给定语言后定义文法表示并提供解释器 | 需定义代表文法的类等级结构 |
| **Iterator** | 顺序访问聚集元素而不暴露内部表象 | 迭代逻辑封装到独立子对象；简化聚集界面 |
| **Mediator** | 包装一系列对象相互作用方式，松散耦合 | 多对多→一对多；Facade解决子系统间、Mediator解决子系统内 |
| **Memento** | 用备忘录对象存储另一个对象内部状态快照 | 不破坏封装条件下将状态外部化 |
| **Observer** | 一对多依赖，主题变化时通知所有观察者 | Java Observable/Observer的经典实现 |
| **State** | 允许对象在内部状态改变时改变行为 | 把行为包装在不同状态对象里 |
| **Strategy** | 将每个算法封装到具有共同接口的独立类中 | 算法可在不影响客户端时变化；与State类似但定义算法组 |
| **Template Method** | 抽象类定义顶级逻辑框架，子类实现细节 | 先制定框架再留细节 |
| **Visitor** | 封装施加于数据结构元素之上的操作 | 数据结构和操作解耦；在已有类层次上添加方法（OCP） |

## 原则与模式的关系

设计模式不是孤立的技巧，而是对设计原则的具体应用：

- **Bridge模式** = 组合优于继承 + 面向接口编程 + SRP + LSP
- **Decorator模式** = Bridge中抽象和实现合二为一 ^[inferred]
- **Strategy模式** = OCP（算法可扩展不修改） + 面向接口编程
- **Observer模式** = OCP（新增观察者不修改主题） + 依赖倒置

**原则选择优先级**：变化是设计的出发点和归宿——先发现变化方向，再选对应原则，最后选具体模式。
