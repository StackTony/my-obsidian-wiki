### ❌ 缺失内容

| 缺失主题 | 说明 |
|----------|------|
| **Harness 可观测性与评测** | `concepts/harness-engineering` 只把可观测性作为 `relationships` 指向 `concepts/llm-observability`，没有 trajectory 评测、离线/在线评测、评测指标与失败分类 |
| **Harness 失败模式的量化诊断** | 现有页面列了失败模式，但缺少"用 trace 定位失败 → 归入 failure taxonomy → 回归测试门禁"的闭环 |
| **Agent Client Protocol（编辑器↔Agent）** | 全库为零。现有 `summaries/acp-protocol` 只讲 IBM 的 Agent Communication Protocol，没有 Zed 的 Agent Client Protocol |
| **ACP 名称歧义** | 两个不同协议共用一个缩写，现有页面未做消歧，读者会把"编辑器接入 Agent"与"Agent 之间通信"混为一谈 |
| **IBM ACP 的治理状态变更** | IBM ACP 官网已挂出横幅：**"ACP is now part of A2A under the Linux Foundation!"**；现有页面仍把 ACP 与 A2A 描述为并列的两层，属于**事实性过时** |
| **协议互操作网关** | A2A 技能暴露为 MCP 资源、MCP 工具封装为 A2A 能力等边界模式，现有页面未覆盖 |

**结论**：Harness 侧已有"骨架"，缺"仪表盘与验收标准"；ACP 侧已有"一个协议"，但**缩写撞名 + 标准合并**两件事都没记录，需要优先纠偏。

## 四、深入推荐

### 4.1 🔥 Databricks：What Is an AI Agent Harness?（Harness 总纲）

| 标题 | 链接 | 类别 | 摘要 | 重点内容 |
|------|------|------|------|----------|
| **What Is an AI Agent Harness?** | [databricks.com](https://www.databricks.com/blog/ai-harness) | 原理介绍 | **Agent = Model + Harness**：模型负责推理，Harness 负责把推理变成可靠动作 | 八大构件：System Prompt、Tools、Sandbox、Filesystem、Memory/Context、Feedback & Self-verification、Guardrails/HITL、Observability；ReAct 四步（Reason→Act→Observe→Repeat，Yao et al. 2022）；七大失败模式：context rot、tool overload、brittle tool wiring、latency、irrelevant retrieval、weak verification、missing guardrails；Prompt/Context/Harness Engineering 三者是包含关系；企业侧 agent sprawl 与共享 Harness 基础设施（治理 + 评测 + 可观测性）；"一次性 Harness"与 NLAH（自然语言 Agent Harness）趋势 |

**关键数据（需注意口径）**：Databricks 把 GPT-5.5 接入 OfficeQA Pro Agent Harness 后得分 52.63%，对比 GPT-5.4 的 36.10%，错误率接近减半。^[ambiguous] 模型与 Harness 同时变化，不能把全部增益单独归因给 Harness——但原文的核心论点是"同一模型换 Harness 也能显著改变排名"，这一点与"强 Harness + 中端模型可胜过弱 Harness + 强模型"的判断一致。

### 4.2 🔥 Databricks：What Is Agent Evaluation?（Harness 的验收标准）

| 标题 | 链接 | 类别 | 摘要 | 重点内容 |
|------|------|------|------|----------|
| **What Is Agent Evaluation?** | [databricks.com](https://www.databricks.com/blog/what-is-agent-evaluation) | 技术分析 | **Agent 评测不是给单个输出打分，而是评测一条动态轨迹** | 非确定性导致多条合法路径；trace-based evaluation 记录每个 span；组件级（router/retrieval/tool args）vs 端到端；单轮 vs 多轮；离线（黄金集/基准）vs 在线（生产流量打分、漂移检测）；指标五类：任务表现、轨迹质量、工具调用、安全合规、效率；方法：LLM-as-judge、人工评审、黄金数据集、工作负载定制基准、A/B；失败分类：幻觉工具调用、无限循环、缺上下文、过期记忆、死胡同推理；CI/CD 部署门禁与持续回归 |

### 4.3 🔥 Zed：Agent Client Protocol 官网（另一个 ACP）

| 标题 | 链接 | 类别 | 摘要 | 重点内容 |
|------|------|------|------|----------|
| **Agent Client Protocol** | [agentclientprotocol.com](https://agentclientprotocol.com/) | 原理介绍 | **编辑器/IDE ↔ 编码 Agent 的标准协议**，类比 LSP | 解决 M×N 集成问题：每个编辑器不必为每个 Agent 写适配，Agent 也不必实现各家编辑器 API；本地 Agent 作为编辑器子进程，走 **JSON-RPC over stdio**；远程 Agent 走 HTTP/WebSocket（远程支持仍在完善）；**尽可能复用 MCP 的 JSON 表示**，但为 diff 展示等编码 UX 增加自定义类型；用户可读文本默认 Markdown |

### 4.4 🔥 Zed：ACP Protocol Overview（协议细节与架构图）

| 标题 | 链接 | 类别 | 摘要 | 重点内容 |
|------|------|------|------|----------|
| **ACP Protocol Overview** | [agentclientprotocol.com/protocol/overview](https://agentclientprotocol.com/protocol/overview) | 技术分析 | **JSON-RPC 2.0 的双向方法集**：Agent 侧与会话生命周期，Client 侧提供文件/终端/权限能力 | Agent 方法：initialize、authenticate、newSession、loadSession、prompt、cancel、logout；Client 方法：requestPermission、fs.readTextFile/writeTextFile、terminal 创建/输出/等待/杀死/释放、elicitation 结构化提问；通知：session updates（message chunks、tool calls、plan、mode 变化、context compaction、用户提示）；路径用绝对路径；`_meta` 扩展位；错误遵循 JSON-RPC 2.0 error object；camelCase 属性 + snake_case 判别值 |

**架构含义**：与 LSP 一样，**Client 是能力提供方**（编辑器有文件系统和终端），**Agent 是能力消费方**（模型需要读写文件、跑命令）。这把"权限审批"放进了协议层：Agent 每次要写文件或跑命令，都可以向 Client 发 `requestPermission`。

### 4.5 IBM：Agent Communication Protocol（已并入 A2A）

| 标题 | 链接 | 类别 | 摘要 | 重点内容 |
|------|------|------|------|----------|
| **Agent Communication Protocol** | [agentcommunicationprotocol.dev](https://agentcommunicationprotocol.dev/) | 原理介绍 | **官网横幅：ACP is now part of A2A under the Linux Foundation!** | 定位 Agent 互操作开放标准；RESTful API（与 JSON-RPC 路线明确对照）；同步/异步、流式、有状态/无状态；在线与离线发现（元数据随分发包走，支持 scale-to-zero）；长任务 async-first；BeeAI 为参考实现；治理在 Linux Foundation。**读这篇的价值不是学 REST 细节，而是确认 ACP 已收敛进 A2A** |

### 4.6 A2A：What Is A2A?（Agent↔Agent 的当前标准）

| 标题 | 链接 | 类别 | 摘要 | 重点内容 |
|------|------|------|------|----------|
| **What Is A2A?** | [a2a-protocol.org](https://a2a-protocol.org/latest/topics/what-is-a2a/) | 原理介绍 | **Agent 不是工具**：A2A 让 Agent 以 Agent 的身份协作，而不是被包成 MCP 工具 | Google 发起、捐赠给 Linux Foundation；HTTPS + JSON-RPC + SSE；Agent Card（`/.well-known/agent-card.json`）发现能力与安全方案；长任务 LRO、流式、推送通知；**不透明执行**：只交换声明的能力与共享上下文，不暴露内部推理/记忆/私有工具；四层 Agent 栈：框架（ADK）→ MCP（上下文）→ 运行时（Agent Engine）→ A2A（互连） |

### 4.7 A2A：A2A and MCP（架构图式分工）

| 标题 | 链接 | 类别 | 摘要 | 重点内容 |
|------|------|------|------|----------|
| **A2A and MCP: Detailed Comparison** | [a2a-protocol.org](https://a2a-protocol.org/latest/topics/a2a-and-mcp/) | 架构图 | **MCP 是纵向加深，A2A 是横向连接** | MCP 让单个 Agent 变深：每接一个 MCP Server 就多一组工具/资源；A2A 让系统变宽：跨团队、跨部门、跨组织连 Agent；工具是良定义、通常无状态的原子能力，Agent 是自主推理、有状态、多轮协商的实体；组合方式：Agent 内部用 MCP，Agent 之间用 A2A；A2A Server 可把良定义技能暴露为 MCP 兼容资源（互操作边界） |

### 4.8 MCP：Introduction（三层协议的底座）

| 标题 | 链接 | 类别 | 摘要 | 重点内容 |
|------|------|------|------|----------|
| **Model Context Protocol** | [modelcontextprotocol.io](https://modelcontextprotocol.io/docs/getting-started/intro) | 原理介绍 | **"AI 应用的 USB-C 接口"**：把 AI 应用连接到外部系统、数据与工具 | Client/Server 架构；标准化工具、资源、提示的暴露方式；一次实现、多处复用；与 A2A 的分工：MCP 不跨 Agent 边界，A2A 不规定 Agent 内部工具如何接 |

## 九、核心术语表

### Harness 相关

| 术语 | 定义 |
|------|------|
| **Agent Harness** | 包裹在 LLM 外部的软件基础设施：提供工具、记忆、工作区、执行环境与护栏，把"推理"变成"可靠动作" |
| **Agent = Model + Harness** | 模型是"大脑"，Harness 是"身体与工作区"，Agent 是两者组成的完整工作系统 |
| **ReAct Loop** | Reason（读上下文决定动作）→ Act（Harness 执行工具/代码/API）→ Observe（捕获结果回灌上下文）→ Repeat，直到任务完成 |
| **System Prompt** | 每次运行都注入的常驻指令：身份、目标、规则；写得差是行为不稳定的常见根因 |
| **Sandbox** | 隔离执行环境，让 Agent 可以跑代码而不污染宿主 |
| **Workspace / Filesystem** | Agent 可读写的工作区与持久化存储，是跨会话状态的载体 |
| **Context Rot（上下文腐烂）** | 对话历史变长后模型推理质量下降；不做裁剪/摘要，长任务必然退化 |
| **Tool Overload（工具过载）** | 一次给模型太多工具，决策变慢且更易选错 |
| **Brittle Tool Wiring（工具接线脆弱）** | 工具描述或调用方式稍变就导致误用，且常常是静默失败 |
| **Weak Verification（弱验证）** | 没有测试环或自检，Agent 过早宣布完成 |
| **Missing Guardrails（护栏缺失）** | 不可逆动作（发消息、删数据、下单）没有审批或人工介入 |
| **Agent Sprawl（Agent 蔓延）** | 各团队各自建 Agent，权限、评测、审计、成本失控；解法是共享 Harness 基础设施 |
| **Disposable Harness（一次性 Harness）** | 为单次任务临时拼装、用完即弃的 Harness |
| **NLAH** | Natural-Language Agent Harness：用自然语言描述 Agent 行为，由共享运行时解释执行，降低搭建门槛 |

### Harness 评测相关

| 术语 | 定义 |
|------|------|
| **Agent Evaluation** | 测量 Agent 在多步、真实场景中的表现：不仅看答案对不对，还看路径是否合理、工具是否用对、是否安全 |
| **Non-determinism（非确定性）** | 同一输入可能走出多条都合法的轨迹；因此不能只比对最终答案 |
| **Trajectory（轨迹）** | Agent 从输入到输出的完整步骤序列，包括推理、工具调用与中间结果 |
| **Trace / Span** | 可观测性记录单位：一次运行是一条 trace，每个步骤是一个 span；评测可对 span 级打分 |
| **Component-level Eval** | 组件级评测：单独测 router、retrieval、参数抽取、工具选择 |
| **End-to-end Eval** | 端到端评测：从输入到最终产出整体测准确性、安全性、成本、指令遵循 |
| **Offline Eval** | 离线评测：用黄金集/基准在部署前跑，做版本比较与调参 |
| **Online Eval** | 在线评测：对生产流量实时打分，检测漂移、回归与新边缘案例 |
| **Golden Dataset** | 人工 curated 的高质量样例集，专门覆盖已知失败模式 |
| **LLM-as-a-Judge** | 用 LLM 按 rubric 给输出或整条轨迹打分；可扩展但有偏差、提示敏感、推理成本 |
| **Deterministic Scorer** | 确定性打分器（schema 校验、字符串/数值断言、单测），适合硬约束 |
| **Failure Taxonomy** | 失败分类学：幻觉工具调用、无限循环、缺上下文、过期记忆、死胡同推理等，用于把个案映射到已知类别 |
| **Deployment Gate** | 部署门禁：新版本必须通过阈值化评测才能上线 |

### 协议相关

| 术语 | 定义 |
|------|------|
| **MCP（Model Context Protocol）** | Agent↔工具/数据的标准：把外部系统以工具、资源、提示的形式暴露给模型；"AI 的 USB-C" |
| **A2A（Agent2Agent Protocol）** | Agent↔Agent 的标准：发现、协商、任务管理、上下文交换；Google 发起，现由 Linux Foundation 治理 |
| **ACP（Agent Communication Protocol，IBM）** | IBM 发起的 Agent 互操作协议，REST/HTTP、同步异步、流式、离线发现；**已并入 A2A** |
| **ACP（Agent Client Protocol，Zed）** | 编辑器/IDE↔编码 Agent 的标准，JSON-RPC 2.0，本地 stdio、远程 HTTP/WebSocket；类比 LSP |
| **Agent Card** | A2A 的能力声明文档，位于 `/.well-known/agent-card.json`，描述技能、端点、安全方案 |
| **Opaque Execution（不透明执行）** | A2A 只交换声明能力与共享上下文，不暴露对方内部推理、记忆与私有工具 |
| **LRO（Long-Running Operation）** | 长任务操作；A2A 用 SSE 流式与异步执行/推送通知处理 |
| **JSON-RPC 2.0** | 轻量远程调用协议；A2A 与 Zed ACP 都基于它，MCP 亦使用 JSON-RPC |
| **stdio 传输** | 本地 Agent 作为编辑器子进程，通过标准输入输出收发 JSON-RPC |
| **LSP 类比** | Language Server Protocol 用标准协议解决编辑器×语言服务器的 M×N 集成；ACP 用同一思路解决编辑器×编码 Agent |
| **Client Capabilities** | Zed ACP 中由编辑器（Client）提供的能力：文件读写、终端、权限审批、elicitation |
| **Session Update** | Agent 向 Client 推送的会话事件：消息块、工具调用、计划、模式切换、上下文压缩 |
| **Elicitation** | Agent 通过 Client 向用户发起的结构化提问（表单/URL 交互） |
| **Permission Request** | Agent 在执行敏感工具前向 Client 请求用户授权 |
| **Agent Skill（A2A）** | Agent 声明的一项能力；良定义、无状态的技能可进一步暴露为 MCP 资源 |
| **Interoperability Gateway** | 协议互操作网关：在 MCP/A2A/ACP 之间做能力映射、认证、审计与成本归属 |
